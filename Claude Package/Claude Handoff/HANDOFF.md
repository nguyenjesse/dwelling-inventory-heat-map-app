## The bug, and why it looked like a zoom bug

`app/js/map.js` pan handler called `viewport.setPointerCapture()` on **every** `pointerdown`
while `scale > 1`. A captured pointer makes the browser retarget the follow-up `click` to the
capture element, so the click landed on `.map-viewport` and never reached the `.area` handler on
the `svg`. The handler early-returns at `scale <= 1` and so never captured at fit — which is the
whole reason fit was the one working zoom level and zooming out "fixed" it.

Fix: arm the pan on `pointerdown`, take capture only after **>3px** of travel (the same
threshold `editor.js:332` already uses), and swallow the trailing `click` after a pan that
actually moved. Comment in `map.js` explains it; don't "simplify" the deferred capture away.

## Gotchas discovered this session

- **The unit suite structurally cannot catch this class of bug** — same lesson as the drag
  lock-up. `map.js` isn't even imported by `tests.js`, and a synthetic `click` would pass
  regardless because pointer-capture retargeting only happens for real input. No unit test was
  added on purpose: it would have been vacuous. The real regression net is a Playwright script
  with `page.mouse`.
- **The zoom toolbar overlays the viewport's top-left corner.** A Playwright test that picks an
  area by `bounding_box()` centre will silently click a `<button>` and report a false failure
  (cost one debug cycle). Always confirm with
  `document.elementFromPoint(x, y).classList.contains('area')` before clicking.
- `page.mouse.click()` is move → down → up with no travel, so it stays under the 3px threshold —
  the fix is testable this way without special-casing.

  _orig = BrowserType.launch
